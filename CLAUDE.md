# CLAUDE.md — DnD_Player

Scheda personaggio interattiva per D&D 5e (**edizione 2014**). Workspace npm in TypeScript (strict): `packages/regole` (`@dnd/regole`: regole, tipi, validazione e cataloghi ufficiali, codice puro condiviso), `apps/web` (React 19, Vite 8, Tailwind CSS v4) e `apps/api` (Fastify 5 su PostgreSQL 17 con `node-postgres`, senza ORM). In produzione: app su Vercel, API su Render (Docker), database su Neon (vedi `docs/adr/` e la sezione "Pubblicazione" del README). I test (Vitest) coprono regole, archivio e rotte. Repository git: `main` è il ramo stabile e protetto (PR e CI obbligatorie; il merge su `main` pubblica); si sviluppa sul branch `sviluppo`.

**Obiettivo: una piattaforma che possa usare chiunque**, con registrazione pubblica e più personaggi per utente. Le regole coprono le 12 classi del Manuale del Giocatore e c'è una procedura guidata per creare personaggi di 1° livello; il personaggio di riferimento è Alston il Breve (Gnomo delle Rocce, Mago della Scuola di Divinazione). Scrivi le nuove funzioni in modo generico, non cablate su Alston o sul Mago.

## Comandi

```bash
docker compose up -d   # PostgreSQL 17 sulla porta 5440 (serve a dev e test)
npm run db:prepara     # migrazioni + cataloghi ufficiali sul database di DATABASE_URL (.env, vedi .env.example)
npm run dev            # API Fastify (porta 3100, tsx watch) + Vite (http://localhost:5173, proxy di /api, aperto alla LAN)
npm run build          # tsc -b (type check di tutto) + vite build (apps/web/dist) + bundle esbuild dell'API (apps/api/dist)
npm run lint           # ESLint (typescript-eslint; react-hooks e react-refresh solo per apps/web)
npm test               # Vitest: progetto "regole" (puro) e "api" (su PostgreSQL, DATABASE_URL_TEST)
npm run migra -w @dnd/api / npm run semina -w @dnd/api / npm run importa -w @dnd/api -- <file>
```

Prima di dichiarare finito un lavoro, esegui `npm test`, `npm run lint` e `npm run build`: devono passare tutti senza errori (i test dell'API vogliono `docker compose up -d`). Ogni nuova regola in `regole.ts` va accompagnata da un test in `packages/regole/src/regole.test.ts`.

- **Dati grezzi e valori derivati.** `CharacterData` contiene solo dati grezzi. Tutto ciò che si calcola (modificatori, TS, abilità, CA, iniziativa, CD e attacco magico, bonus competenza, slot massimi, limite di preparazione, soglia XP, attacco e danno delle armi) viene da `derivate(char)`, calcolata a ogni render in `App` e passata alle tab come `d`. **Non memorizzare nello stato un valore derivabile e non scriverlo a mano nel JSX:** aggiungilo a `derivate()`.
- **Stato.** Un solo `useState<CharacterData>` in `App`, aggiornato in modo immutabile con `setChar(prev => ...)`. Le tab ricevono `char`, `d` e `setChar`. Lo stato solo di interfaccia (input dei form, ultimo tiro) resta locale nella tab.
- **Risorse, condizioni ed effetti.** In `CharacterData` ci sono solo dati grezzi: `risorseUsate` (usi spesi per id), `condizioni` (id), `indebolimento` (0–6), `effetti` (`{ id, valore? }`) e `note`. Massimi, ricariche, CA e vantaggio/svantaggio si derivano dalle definizioni in `packages/regole/src/dati/`. Gli effetti di un incantesimo si attivano da soli al lancio (`effettoDaIncantesimo`, per nome). I d20 passano da `conSuggerimento()` (`apps/web/src/tiroDadi.ts`) per preselezionare vantaggio o svantaggio; non ricalcolarli a mano. Per aggiungere una risorsa o un effetto basta una voce in `RISORSE` / `EFFETTI` e un test.
- **Tiri di dado.** Ogni tiro passa da `chiediTiro()` o, per i d20, da `chiediD20()` (`apps/web/src/tiroDadi.ts`); per i danni c'è `tiraDanni()`. Tutti aprono `components/DialogoTiro.tsx`. L'utente sceglie se inserire i risultati dei propri dadi fisici o se far tirare l'app. È una richiesta esplicita dell'utente: **non chiamare mai `tiraD` direttamente in una funzionalità**. `chiediTiro` restituisce una Promise con i risultati (`null` se l'utente annulla), quindi gli handler sono `async`. Il tiro avviene **fuori** dall'updater di `setChar`, perché in StrictMode React chiama l'updater due volte, e gli esiti vengono passati alle funzioni pure (vedi `riposoLungo(c, presagio)`). `App` crea `chiediTiro` e `chiediD20` con `useRichiestaTiro()` e li passa alle tab che ne hanno bisogno.
- **Slot.** `slotSpesi` è un array di 9 elementi (indice 0 = slot di 1° livello). I massimi vengono da `slotMassimi(incantatore, livello)`; per il patto del Warlock solo il livello degli slot ha un valore (gli altri sono 0 e non si mostrano).
- **Classi.** Le regole stanno nel codice (`packages/regole/src/dati/classi.ts`), perché servono a `derivate()` anche offline; i testi dei privilegi stanno nel catalogo. `incantatoreDi(classe, sottoclasse)` restituisce anche i terzi incantatori. Privilegi che cambiano i calcoli si riconoscono per nome (`Robustezza Nanica`, `Resilienza Draconica`, `Astuzia Gnomesca`).

## Archivio (PostgreSQL)

- **Tutti i dati del personaggio sono in tabelle**, non in un JSON: `personaggi` (colonne per info, PF, monete, lore, `avatar`…) più le tabelle figlie `personaggio_caratteristiche`, `_abilita`, `_slot`, `_presagio`, `_xp`, `_oggetti` (l'inventario è proprio del personaggio), `_risorse`, `_condizioni`, `_effetti`, `_note`, `_note_campi` (`indebolimento` è una colonna di `personaggi`). Nomi `citext` (senza distinzione di maiuscole), flag `boolean`, date `timestamptz`, ordine delle liste in colonne `ordine`.
- **Cataloghi per la creazione**: `razze` (con `razza_madre_id` per le sottorazze, `razza_competenze`, `razza_privilegi`), `background` (`background_competenze`, `background_oggetti`), `armature`, `classe_privilegi(classe, sottoclasse, livello)`, `incantesimo_classi`. Il personaggio ha `taglia`, `armatura_id`, `scudo` e `personaggio_competenze(tipo: lingua/strumento/arma/armatura)`.
- **Cataloghi condivisi** `incantesimi`, `armi`, `privilegi`, collegati con le tabelle ponte `personaggio_incantesimi` (con `preparato`), `personaggio_armi` (chiave `personaggio_id, ordine`: una riga per copia, con `bonus`, munizioni, durabilità e `rotta`), `personaggio_privilegi`. Ogni voce ha `creato_da`: NULL = ufficiale (seed), altrimenti l'utente che l'ha aggiunta. Per ora chiunque può aggiungere voci (sono condivise con tutti); in produzione si userà solo il catalogo ufficiale.
- **L'API resta "a documento"**: il client legge e scrive `CharacterData` intero. Su `PUT` il server completa i campi assenti con quelli salvati (`completaConEsistente`: un client con una versione vecchia dell'app non deve cancellare i campi che non conosce), lo valida con `daJSON()` e lo scompone (`scomponi`, dentro la transazione della revisione); su `GET` lo ricompone (`componi`). Il client non conosce le tabelle.
- **Le voci di catalogo si risolvono per nome** (privilegi: nome + fonte, senza distinguere maiuscole; un privilegio che migliora con il livello ha una sola voce, con le soglie nella descrizione), mai per id: così funzionano l'import dei vecchi JSON e le voci nuove. Un nome sconosciuto crea una voce con `creato_da`. I campi di una voce esistente vengono sempre dal catalogo: una `PUT` non può modificarla. `concentrazione` resta il nome nel JSON (`concentrazione_id` nell'archivio).
- **Seed**: per correggere o aggiungere voci ufficiali modifica `packages/regole/src/semi/`. `aggiornaCataloghi` (`npm run semina`) fa l'upsert, ma solo sulle voci con `creato_da IS NULL`. **Non gira all'avvio del server**: la esegue il workflow Deploy dopo le migrazioni (in locale `npm run db:prepara`).
- **Cambiare lo schema**: aggiungi `apps/api/migrazioni/NNN_descrizione.sql` con il numero successivo; non modificare mai una migrazione già su `main`. Il deploy applica le migrazioni **prima** di aggiornare il server, quindi devono funzionare anche con il codice precedente: aggiungi colonne (con `DEFAULT`) e tabelle; rinomina o togli solo in due deploy. I dati degli utenti non devono andare persi. Se aggiungi un campo a `CharacterData`, aggiorna `personaggioVuoto()`, `normalizza()`, `scomponi` e `componi` (e `SQL_SCHEDA`), e il test di andata e ritorno in `apps/api/test/personaggi.test.ts`.
- **Prestazioni**: in produzione ogni query attraversa la rete (Render ↔ Neon). Niente query in un ciclo: usa `inserisciRighe`, `ANY($1::tipo[])`, `unnest` e `json_agg`, come in `scomponi`, `componi` e `idVoci`.
- **Test**: usano solo `DATABASE_URL_TEST` (mai `DATABASE_URL`). Per un test che tocca il database usa `await archivioDiProva()`.

## Accesso

- Registrazione pubblica (`POST /api/registrazione`): username 3–30 caratteri `a-z 0-9 . _ -` (senza distinzione di maiuscole), password di almeno 8 caratteri.
- **Modifica dell'account** (`FinestraAccount`, aperta dal pulsante con lo username nell'intestazione): `PUT /api/account/username` e `PUT /api/account/password` chiedono sempre la password attuale e applicano le stesse regole della registrazione. Una password attuale sbagliata risponde **403** (non 401, che per il client vuol dire sessione scaduta) dopo 1 s. Il cambio di password chiude le sessioni degli altri dispositivi e lascia aperta quella in uso; il cambio di username non tocca le sessioni.
- Senza una sessione valida l'API risponde 401 a tutto tranne registrazione e accesso. Un personaggio di un altro utente risponde 404, come se non esistesse.
- Le password sono hash `scrypt$sale$hash`. Delle sessioni si salva solo lo SHA-256 del token; il token sta nel cookie `dnd_sessione` (HttpOnly, SameSite=Strict, `Secure` in produzione, 30 giorni). Un accesso fallito risponde dopo 1 s. **Non scrivere password in chiaro nel codice, nei test o nella documentazione.**
- Limiti ai tentativi (`@fastify/rate-limit`, risposta 429 con `{ errore }`): accesso 10 ogni 5 minuti per username, registrazione 10 l'ora per IP, modifiche dell'account 10 ogni 5 minuti per sessione. `trustProxy` è attivo (Vercel e Render davanti).
- Un archivio nuovo non ha utenti.
- Se il server risponde 401 durante l'uso, `useSincronizzazione` chiama `onSessioneScaduta` e `App` torna al login; con 404 chiama `onInesistente` e `App` torna all'elenco. Le modifiche non inviate restano in `localStorage`.

## Salvataggio e sincronizzazione

- Il `localStorage` (`dnd_personaggio_<id>` e `dnd_personaggio_<id>_sincronizzazione`) è una copia offline: la scheda si mostra subito da lì, poi arriva quella del server. Prima di aprire un personaggio senza copia locale, `App` lo scarica.
- Ogni modifica va subito nel `localStorage` e dopo 500 ms al server con `PUT { dati, revisione }`. Il server accetta solo se la revisione coincide, altrimenti risponde 409 con la versione attuale e il client chiede con `confirm()` quale tenere. Gli aggiornamenti degli altri dispositivi si scaricano all'avvio, al focus o al ritorno sulla pagina, e ogni 15 s.
- Import JSON: dalla schermata dei personaggi crea un personaggio nuovo (`POST /api/personaggi`); dentro la scheda sostituisce quella aperta. Non c'è più "Ripristina ai dati iniziali".
- In sviluppo `server.host` è `true`: l'app è raggiungibile dalla rete locale su http. In produzione tutto passa da https (Vercel e Render).
- Render gratis si spegne dopo 15 minuti: all'avvio `sessioneAttuale` riprova sugli errori 502/503/504 e `App` mostra "Avvio del server in corso…". La sincronizzazione ogni 15 s tiene il server acceso durante il gioco.
- `daJSON()` (`packages/regole/src/scheda.ts`) valida i dati e li normalizza, completando le sezioni mancanti con `personaggioVuoto()`. Converte anche il vecchio formato senza `versione` (`migraV1`). Se il cambiamento a `CharacterData` non è compatibile, porta `versione` a 3 e aggiungi una migrazione.

## Attenzione

- **`apps/web/src/index.css` deve restare minimale.** Tailwind v4 mette le utility in `@layer` e qualunque CSS fuori dai layer vince su di esse. Il vecchio CSS del template rendeva il nome del personaggio illeggibile. Gli stili vanno scritti come classi Tailwind nel JSX.
- Tailwind v4 si configura tramite il plugin `@tailwindcss/vite`: non ci sono `tailwind.config.js` né `postcss.config.js`.
- `react-refresh/only-export-components`: i file in `apps/web/src/components/` devono esportare solo componenti. Costanti e funzioni condivise vanno in `regole.ts`.
- `packages/regole` gira nel browser e in Node: niente DOM, niente API di Node e niente React (il suo `tsconfig.src.json` non ha né `DOM` né `@types/node`). Si importa con il percorso del file: `@dnd/regole/regole.ts`, `@dnd/regole/dati/classi.ts`. I pacchetti espongono i sorgenti `.ts` (risoluzione `bundler`): niente build del pacchetto condiviso.
- Le porte 3000, 5173 e 5432 sono spesso occupate da altri progetti in Docker: l'API di sviluppo usa la 3100 e Postgres la 5440; Vite passa da solo alla prima porta libera.
- Tipi da React: usa `import { type FormEvent } from "react"`, non `React.FormEvent` (con `verbatimModuleSyntax` il namespace globale non è disponibile).

## Convenzioni

## Regole implementate (5e 2014)

- **Classi**: le 12 del Manuale del Giocatore. Dado Vita, TS e competenze da `CLASSI`; slot di incantatori completi, mezzi (Paladino, Ranger dal 2°), terzi (Cavaliere Mistico, Mistificatore Arcano dal 3°) e patto (Warlock, recuperati anche con il riposo breve). CD e attacco magico con la caratteristica della classe; chi non incanta per classe usa quella razziale per i trucchetti di razza (`CARATTERISTICA_MAGICA_RAZZIALE`). Preparati = livello + mod (Paladino: metà livello + mod); Bardo, Ranger, Stregone, Warlock e i terzi incantatori hanno incantesimi conosciuti.
- **Creazione** (1° livello): razza e sottorazza con i loro bonus e scelte, classe con abilità e sottoclasse (solo Chierico, Stregone e Warlock al 1°), caratteristiche con 4d6 senza il dado più basso (sei tiri con `chiediTiro`, poi si assegnano), background (le abilità ripetute si sostituiscono), equipaggiamento iniziale a gruppi di scelta, incantesimi iniziali dal catalogo (chi prepara dall'intera lista riceve tutti quelli di 1° livello della classe), dettagli. PF = Dado Vita massimo + COS.
- **CA**: armatura indossata (con il limite di DES) e scudo +2; senza armatura la migliore tra 10 + DES, Difesa Senza Armatura (Barbaro +COS, Monaco +SAG senza scudo) e Resilienza Draconica (13 + DES). Avvisi per svantaggio in Furtività e Forza sotto il minimo. Armatura o scudo senza competenza: svantaggio a prove, TS e attacchi di FOR e DES (`suggerimentoTiro`) e niente incantesimi (`d.incantesimiBloccati`). `daJSON` completa con quelle della classe le schede che non hanno competenze né in armi né in armature (salvataggi vecchi).
- Armi: accurate con la migliore tra FOR e DES, a distanza con la DES, le altre con la FOR. Il bonus di competenza si aggiunge solo se `competenzeAltre.armi` copre l'arma (categoria, nome o plurale), altrimenti l'arma mostra "Non competente"; il bonus magico dell'arma si somma ad attacco e danni. Si aggiungono dal catalogo o personalizzate (`PannelloArmi`). Munizioni e durabilità (facoltative) scendono di 1 a ogni tiro per colpire confermato (`usaArma`); a munizioni 0 non si attacca, a durabilità 0 l'arma si rompe. "Danneggia" lascia a qualsiasi arma un numero di colpi prima di rompersi (`danneggiaArma`: abbassa la durabilità o, senza durabilità, imposta `danneggiata`; nell'archivio è `durabilita_rimasta` con `durabilita_massima` NULL). "Recupera" restituisce metà delle munizioni spese; "Ripara" riporta la durabilità al massimo e toglie il danno. Archi e balestre iniziali partono con 20 munizioni.
- Riposo lungo: PF al massimo, recupero di metà dei Dadi Vita (minimo 1), slot ripristinati, nuovo Presagio (solo Scuola di Divinazione), Recupero Arcano di nuovo disponibile.
- Riposo breve: un unico pannello (`components/PannelloRiposoBreve.tsx`), aperto dal pulsante nell'intestazione. Contiene la durata in ore (minimo 1), i Dadi Vita della classe (+ COS ciascuno, tirabili a più riprese), il Canto di Riposo di un bardo del gruppo (solo se si spende almeno un Dado Vita), il recupero di 1 PF dopo 1d4 ore se si è stabilizzati a 0 PF, il Recupero Arcano per il Mago (slot per ⌈livello/2⌉ livelli complessivi, massimo il 5° livello, una volta al giorno) e il recupero degli slot del patto. Nulla viene applicato finché non si preme "Completa riposo": allora `riposoBreve()` applica l'esito.
- Divinazione: Presagio con 2d20, che diventano 3d20 dal 14° livello. Nel dialogo di ogni tiro per colpire, TS o prova (richieste con `tipo`, impostato da `conSuggerimento`) i dadi non usati (`d.presagioDisponibile`) sostituiscono il d20; `App` li segna con `usaPresagio`. Il d20 rapido non li offre.
- PF: il danno consuma prima i PF temporanei. Cambiare la COS modifica retroattivamente i PF massimi.
- Tiri d20: normale, vantaggio o svantaggio. Prove di caratteristica pure (clic sul modificatore o su "Prova"), TS e abilità. I TS di INT, SAG e CAR ricordano l'Astuzia Gnomesca a chi ce l'ha.
- Danni: dopo un tiro per colpire con un'arma si tirano i danni (una o due mani per le armi versatili), anche in più parti (`Danni[]`). Su un 20 naturale (19 o 18 con il Critico Migliorato del Campione, `sogliaCritico`) si raddoppiano i dadi di tutte le parti, non il modificatore; il Critico Brutale aggiunge dadi dell'arma in mischia. Il totale non scende sotto 0.
- Privilegi d'attacco, riconosciuti da classe, sottoclasse e livello (non dal nome del privilegio): Attacco Extra (solo mostrato), Attacco Furtivo (⌈livello/2⌉d6 con armi accurate o a distanza, facoltativo e preselezionato con vantaggio), Punizione Divina (dal 2°, in mischia: 2d8 +1d8 per slot oltre il 1°, massimo 5d8, +1d8 contro immondi e non morti; lo slot si spende con `spendiSlot` solo se il tiro dei danni viene fatto), Punizione Divina Migliorata (+1d8 radiosi dall'11°), Arti Marziali (Monaco senza armatura né scudo: con le armi da monaco la migliore tra FOR e DES e il dado d4–d10 se più alto). Il colpo senz'armi è offerto a tutti: 1 + FOR, oppure il dado delle Arti Marziali.
- Aggiunta di incantesimi: il pulsante "Cerca incantesimi" del grimorio apre `RicercaIncantesimi` (lista della classe preselezionata, più voci in una volta, quelle già presenti non si scelgono); l'incantesimo personalizzato resta in un modulo a parte.
- Incantesimi: cliccando il nome nel grimorio si apre `FinestraIncantesimo`. Si lancia con uno slot di livello pari o superiore (se preparato, o sempre per chi li conosce), come rituale senza slot, oppure come trucchetto. Lo slot viene speso e si tirano attacchi e danni, con il danno che scala per slot o per livello del personaggio. Un 1 naturale non fa danni. Un incantesimo aggiunto senza scheda nel catalogo si può lanciare ugualmente, ma solo per spendere lo slot.
- Incantesimi di sottoclasse (`packages/regole/src/dati/incantesimiSottoclasse.ts`): domini del Chierico (dal 1°), giuramenti del Paladino (dal 3°) e terreni del Circolo della Terra (dal 3°, secondo il privilegio "Terreno del Circolo") sono sempre preparati: `d.semprePreparato(nome)` li lascia lanciare, `preparatiAttuali` non li conta e nel grimorio mostrano la fonte al posto del pulsante di preparazione. Si aggiungono da soli alla creazione (Chierico) e alla salita di livello; il grimorio avvisa di quelli mancanti e li aggiunge dal catalogo. I patroni del Warlock ampliano solo la lista (`d.incantesimiAmpliati`, indicati nel riepilogo della salita). Il confronto è per nome: un incantesimo con lo stesso nome aggiunto a mano vale come quello di sottoclasse.
- Concentrazione: lanciare un incantesimo con `concentrazione` la imposta (con conferma se ne interrompe un'altra). Ogni danno richiede un TS su COS con CD max(10, danno/2). Si perde a 0 PF e con i riposi.
- 0 PF (`statoVita`: in piedi / morente / stabile / morto): i TS contro morte (10+ successo, 1 = due fallimenti, 20 = 1 PF) si tirano nella card dei PF. Un danno a 0 PF vale un fallimento. Se il danno oltre lo 0 raggiunge i PF massimi è morte istantanea. La cura azzera i tiri. Il riposo lungo richiede almeno 1 PF.
- Risorse di classe: card nella tab Statistiche con un pallino per uso (o un contatore per le riserve di punti, come Imposizione delle Mani). Il riposo breve ricarica quelle "breve" (elencate nel pannello), il lungo tutte. L'Ispirazione Bardica diventa "breve" dal 5° livello. Il Mago usa ancora `recuperoArcanoUsato`.
- Condizioni ed effetti (card nella tab Statistiche, chip nell'intestazione): le condizioni e l'indebolimento suggeriscono vantaggio o svantaggio nel dialogo del tiro (annullandosi a vicenda) e segnalano il fallimento automatico dei TS di FOR/DES; le condizioni di incapacità interrompono la concentrazione. Indebolimento 4 dimezza i PF massimi (`pfMassimiEffettivi`), il riposo lungo lo riduce di 1. Ira (spende un uso, +danni in mischia con la Forza) e Attacco Sconsiderato (dal 2° livello) solo per il Barbaro. Dal pannello si attivano solo i propri privilegi e gli effetti con `bersaglio: "altri"` (lanciati da un alleato); quelli solo personali (Scudo, Immagine Speculare) partono dal lancio (`attivaEffetto(c, id, { daIncantesimo: true })`). Lanciando un incantesimo con effetto su altri si sceglie se applicarlo a sé. Armatura Magica, Scudo, Scudo della Fede, Pelle Coriacea e Velocità modificano la CA; Immagine Speculare ha il contatore dei duplicati. Il riposo breve chiude gli effetti brevi, il lungo tutti.
- Note: tab Note con categorie (sessione, PNG, obiettivo con casella "fatto", altro), ciascuna con i suoi campi (`packages/regole/src/dati/note.ts`: per i PNG razza, classe, ruolo, luogo, fazione, atteggiamento, stato; per gli obiettivi committente, ricompensa, priorità, scadenza…), salvate man mano.
- Scelte di privilegio (`packages/regole/src/dati/scelte.ts`): opzioni del catalogo con una `fonte` propria ("Metamagia", "Stile di Combattimento", "Terreno del Circolo"), salvate come privilegi, senza campi nuovi nella scheda. Si scelgono alla creazione (lo stile del Guerriero), nel pannello di salita di livello (quelle dovute al nuovo livello, obbligatorie se il catalogo è raggiungibile) e nella card "Scelte da completare" della tab Progresso (`sceltePendenti`). Il Campione ha un secondo stile al 10°; Paladino e Ranger hanno i loro stili ammessi.
- Stili di combattimento: Difesa +1 CA con armatura, Tiro +2 a colpire con armi a distanza, Duellare +2 ai danni in mischia a una mano (non su armi "Due mani" né sul tiro versatile a due mani); Combattere con Armi Possenti è una nota nel dialogo dell'attacco (`attaccoArma().note`), Protezione e Due Armi restano descritti.
- Stregone: in `FinestraIncantesimo` si scelgono le metamagie conosciute e al lancio si spendono i Punti Stregoneria (`usaMetamagia`; il Gemello costa il livello a cui si lancia, 1 per i trucchetti), con il lancio bloccato se non bastano. Fonte di Magia nella card dei Punti Stregoneria: `slotInPunti` (solo se i punti spesi bastano a riceverli tutti) e `puntiInSlot` (2/3/5/6/7 punti; recupera uno slot speso, quindi non supera i massimi).
- Privilegi: nella tab Lore si aggiungono (nome, fonte, descrizione: talenti, oggetti magici…) e si tolgono con conferma.
- Avatar: `info.avatar` è un data URL (JPEG 256 px, `ridimensionaAvatar`) che viaggia con la scheda; `daJSON` accetta solo `data:image/(png|jpeg|webp);base64` fino a 300 000 caratteri. Si mostra nell'intestazione, nella creazione e nell'elenco dei personaggi.
- Salita di livello (tab Progresso): PF medi del Dado Vita della classe + COS (+1 con Robustezza Nanica o Resilienza Draconica), un Dado Vita, i privilegi del nuovo livello dal catalogo e la sottoclasse quando si raggiunge il suo livello. Il pannello chiede anche l'aumento dei punteggi (+2 a una o +1 a due, massimo 20; ai livelli 4, 8, 12, 16, 19 più gli extra della classe) oppure un talento (privilegio con fonte "Talento", senza effetti automatici), le scelte di privilegio e i nuovi trucchetti e incantesimi (conosciuti o i 2 da copiare nel libro) dal catalogo, filtrati per lista della classe più la lista ampliata del patrono e per livello di slot (`incantesimiDaImparare`). Gli incantesimi sono facoltativi (il catalogo può averne pochi); aumento, sottoclasse e scelte sono obbligatori. L'aumento si applica dopo i PF del livello, quindi un aumento della COS vale per tutti i livelli. Il pulsante "Cerca privilegi mancanti" aggiunge alla scheda quelli fino al livello attuale che non ha (`GET /api/classi/:classe/privilegi?fino=n`). Lo scambio di un incantesimo conosciuto alla salita non c'è ancora.

Non ancora implementati: effetti dei privilegi sui calcoli oltre a quelli elencati sopra (Suppliche Occulte e Manovre sono solo descritte; le risorse tengono il conto degli usi ma non applicano l'effetto), multiclasse, catalogo dei talenti e loro effetti, scambio di un incantesimo conosciuto alla salita di livello, equipaggiamento in alternativa all'oro iniziale, eliminazione di account e personaggi, recupero della password dimenticata, limitazione del catalogo alle sole voci ufficiali, altri effetti attivi oltre a quelli in `EFFETTI`, backup periodico del database oltre alla storia di Neon.
